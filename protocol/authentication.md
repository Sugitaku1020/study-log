# 認証
認証は「あなたは誰か?」を確認する.別概念として認可は「あなたに何を許可するのか?」を制御する。多くの仕組みは認証+認可を一体で扱う.

##  1. Basic認証
ユーザーの`username:password`という秘密情報をリクエストの度に`Authorization`ヘッダに載せてサーバーへ送る.

### 具体的な流れ
1. ユーザーがブラウザでアクセス
2. ユーザーがID/パスワードのダイアログを表示
3. 入力値をBase64エンコードしてリクエストに載せる
4. サーバーがでコードして認証情報を検証

認証にもちいる秘密情報を「HTTPリクエストヘッダ」そのものに格納している。リクエストの度に毎回送信される。

### 限界
- 資格情報を毎回ネットワークに流してしまう(HTTPSでなかったら外から丸見えになる)
- 権限の粒度がない(あるかないかの2択)
- 第三者への権限移譲は不可能
→ ユーザー本人が毎回直接アクセスするという前提の方式

### Base64について
base64は64進数を意味し、すべてのデータをアルファベット([a-z], [A-Z])や一部の記号(+, /)の64文字で表すエンコード方式。
パディングとして末尾の記号に`=`を使用するから厳密には65文字。
#### 導入背景
かつての電子メールを送るためのプロトコルSMTPではASCIIしかおくることができなかった。MIME(Multipurpose Internet Mail Extensions)という規格が登場し、その中でbase64のデータ変換方法が定められた。
送信と受信側でMIMEに従ったエンコード、デコードによってメールを通じて画像や音声などの送受信が可能になった。

## 2. session認証
ログイン時に一度だけ、ID/パスワードを検証し、サーバー側にセッション情報を格納する。以降はクライアントの`Cookie`に保存されたセッションIDを毎回送ることで認証する.

### 具体的な流れ
1. ユーザーがID/パスワードでログイン
2. サーバーがDB等にセッションID → ユーザー情報を保存する。
3. セッションIDをCooKieとしてブラウザへ返す.
4. 以降のリクエストでブラウザが自動的にCookieを送信
5. サーバーがセッションIDを照合して認証

秘密情報の格納場所は「ブラウザのCookie」と「サーバーのセッションストア」

### 限界
- ブラウザ前提の設計なのでAPI連携・モバイルに不向き
(ブラウザ以外のクライアントにはこの仕組みが標準では備わっていない)
- セッションストアをスケールさせる必要がある
- 第三者アプリに限定的な権限だけを渡すことができない。

→ 同一アプリ内で簡潔する前提の方式

## 3. APIキー認証
アプリケーションに固定の秘密情報(APIキー)を発行し、リクエストのヘッダやクエリパラメータに埋め込んで送信する。

### 具体的な流れ
1. 管理画面などでAPIキーを発行
2. クライアントがリクエスト時にキーを送信
3. サーバーがキーをDBと照合してアクセスを許可

秘密情報(APIキー)の格納場所は「クライアントの環境変数や設定ファイル」。サーバーtoサーバー通信で多い。

### 限界
- APIはアプリケーション単位の認可であり、どのユーザーが操作しているのかは識別できない
- キーが漏れると全権限が奪われる.
- ユーザーの同意・委譲という概念がない

→ アプリケーション単位の認可に適した方式

## 4. SAML(Secturity Assertion Markup Language)
エンタープライズ向けのシングルサインオン(SSO)を実現するXMLベースのプロトコル.
SAMLと呼ばれるXML文書を用いる.IdP(Identity Provider)が「このユーザーは認証済みです」と署名して発行する証明書のようなもの、おおまかには以下の形。
IdP: ユーザーの認証情報を一元管理して、本人確認の結果を各種アプリやクラウドサービスへ提供する仕組み・サービス(Okta, Microsoft Entra ID, Google Cloud Identityなど)

```xml
<!-- 誰が・誰に・いつまで有効か、ユーザー属性をXMLで表現 -->
<saml:Assertion ...>
  <saml:Issuer>https://idp.example.com</saml:Issuer>  <!-- 発行者 -->
  <saml:Subject>
    <saml:NameID>tanaka@example.com</saml:NameID>      <!-- ユーザー -->
  </saml:Subject>
  <saml:AttributeStatement>
    <saml:Attribute Name="role">
      <saml:AttributeValue>admin</saml:AttributeValue> <!-- 属性 -->
    </saml:Attribute>
  </saml:AttributeStatement>
  <ds:Signature>...</ds:Signature>                     <!-- デジタル署名 -->
</saml:Assertion>
```
SAMLassertionは主にユーザーのブラウザ経由でSPへ届けられる。
1. IdPがHTMLフォームにBase64エンコードしたアサーションを埋め込む。
2. ブラウザが自動的にそのフォームをSP(Service Provider)へPOST送信する(HTTP POST Binding)

アサーション自体はサーバー間で直接やり取りされるのではなく、ブラウザが仲介する。モバイルアプリとの相性が悪い理由となる.

### SAMLのSSO全体フロー

| 役割 | 英語 | 例 |
| --- | --- | --- |
| ユーザー | User / Principal | 社員のブラウザ |
| サービスプロバイダ | SP (Service Provider) | Salesforce や Slack |
| ID プロバイダ | IdP (Identity Provider) | Okta、旧Azure AD |

```
[ユーザー] → [SP（Salesforce）] にアクセス
     ↓
[SP] 「うちは認証しない。IdPへ行って」→ SAMLリクエストを生成し、ユーザーをIdPへリダイレクト
     ↓
[ユーザー] → [IdP（Okta）] でログイン（社内のID/パスワード）
     ↓
[IdP] 認証成功 → SAMLアサーション（XML）を生成・署名
     ↓
[IdP] → ユーザーのブラウザ経由でSAMLアサーションをSPへPOST
     ↓
[SP] アサーションの署名を検証して、ユーザーのログインを許可
```
### 強み
- デジタル署名によりアサーションの改竄を検出できる
- エンタープライズで実績が豊富(Okta, Azure AD, Google Workspaceなど)
- 詳細なユーザー属性(ロール、部署など)を安全に渡せる
### 限界
- XMLの解析が複雑で実装が重い
- モバイルアプリ・ネイティブアプリとの相性が悪い(ブラウザリダイレクト前提)
→ 企業内ID統合・エンタープライズSSOの標準。モダンなWeb APIとは相性が悪い。

## 5. OAuth
インターネット上のサービス同士が安全に情報をやり取りするための仕組み。ユーザーはIDやパスワードを直接そのサービスに渡す必要がなく、代わりにGoogleなどの信頼できる提供元に一度だけ認証してもらい、その証明書を相手のサービスに提供することでアクセス可能になる。
これによって、複数のサービスで同じパスワードを入力するリスクを下げられ、利便性と安全性を両立できる。

現在はOAuth1.0の後継として策定されたOAuth2.0が利用される。違いとしては設計仕様と仕組みの洗練度。

最初に登場したOAuth 1.0は、サービス間でユーザーの認証情報を共有せずに安全にアクセス権を渡すという目的は果たしたが、仕様がやや複雑で、拡張性や運用面で課題があった。

OAuth 2.0では、認可コードやアクセストークンの仕組みが整理され、スマートフォンアプリやWebサービスなどさまざまな利用環境に対応できる柔軟さを備える。

OAuth1.0は認証にも使われがちだったが、OAuth2.0になって認可を中心に設計される。OpenID Connectと組み合わせることで認証/認可が正しく利用できるようになった。

#### 流れ(提供元はGoogleとする)
1. 「Googleでログイン」を押すと、画面がGoogleに切り替わり、Googleが本人認証と権限の範囲を尋ねる
2. ユーザーが許可すると認可コードをアプリに返す
3. それをもとにアクセストークン(短時間だけ有効な入館証みたいな感じ)をGoogleから受け取り、それを提示して必要なデータにアクセス

アクセストークンは時間が経つと失効するが、必要に応じて長持ちな更新用鍵(リフレッシュトークン)を生成できる。

#### OAuthのリスク
1. 許可画面の内容を確認せずに承認するリスク
- 必要のない範囲の情報まで相手に渡ってしまう可能性
2. アクセストークンの漏洩や盗聴による不正利用
- トークンが第三者に盗まれると、パスワードを知らなくても正規のユーザーに成りすましてシステムを利用される恐れがある(トークンを平文で保存したり、通信経路を盗聴されていると危険). 安全な保存方法を考える必要がある
3. トークンの有効期限を長く設定しすぎるリスク
- 漏洩した場合、有効期限が長いほど不正利用が続く。できるだけ短くしてリフレッシュトークンを利用する。
